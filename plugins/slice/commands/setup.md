Set up slice in the current repo. This runs in an interactive session because the run profile cannot edit `.git`, `.husky` or `.claude`. Without a person to ask, use the defaults named below and say so. Change nothing that exists without showing it first; merge instead of skipping.

0. Empty repo (no commits, or nothing but a README and licence): first run "new" mode, then continue with step 1.
   - Ask with AskUserQuestion, one question each, your recommendation first: the goal in one sentence, the stack, the first path a user walks end to end.
   - Create the skeleton with the stack's official generator (`npm create vite@latest`, `uv init`, `cargo new`, `go mod init`, `gradle init`), never from memory or a template of your own.
   - Write `NORTHSTAR.md`, at most 30 lines: goal, non-goals, how success is measured, the first stage.
   - Write one ADR `docs/adr/0001-stack.md` with the stack choice and its reasons, and let the person confirm it. Further ADRs only when the person decides a direction.
   - Add a `verify-*` make target for the first user path that fails on an assertion now. It is the first red proof.
1. Look. Stack, package manager, test commands, CI files, existing `Makefile`, `AGENTS.md`, `CLAUDE.md`, `.claude/`. Count committers with `git shortlog -sn HEAD | head`; with any other committer add no new tracked tooling files the repo does not already have and put the verification section in a git-excluded `CLAUDE.local.md` that starts with `@AGENTS.md` when the repo has one.
2. Measure the suite and split it by time: while editing seconds (`make test-affected FILES=…`), pre-commit at most 60 s (`make check`), PR minutes (`make verify`, CI). Ask one AskUserQuestion about tests to delete or merge, with your recommendation first; default: keep all.
3. Write what is missing:
   - `Makefile` targets `check`, `verify`, `test-affected` with worker limits (cores minus 2, at most 4), plus an end-to-end `verify-*` target for the repo's main behaviour with real data.
   - In UI repos also `scripts/ui-check.mjs` copied from `${CLAUDE_PLUGIN_ROOT}/scripts/ui-check.mjs`, so make targets can call it.
   - `scripts/slice-lock.sh` copied from `${CLAUDE_PLUGIN_ROOT}/scripts/slice-lock.sh`; the Makefile and the hook run their commands through it.
   - A pre-commit hook that runs `make check` through the lock.
   - In repos without other committers that have a GitHub remote: a CI job for `make check` and the proofs a hosted runner can run.
   - In `AGENTS.md` (or `CLAUDE.local.md` with other committers) a section headed `## Verification`, at most 15 lines: the three make targets, the tiers, "before a commit ask the slice tool to prove; never trust your own run", and the scope contract. Without other committers: if `CLAUDE.md` is missing create it with one line `@AGENTS.md`; if it exists and lacks that line, add it.
4. Repos with an app that needs more than a standard launch (database, env file, multi-step build), and all UI repos: suggest `/run-skill-generator` and make ports and paths in the recipe come from `.slice-env`. The bundled `/run` and `/verify` follow that recipe. Never write `.claude/skills/verify/`: the bundled `/verify` records its own recipe there, and a file at the repo root replaces it. Suggest `excludedCommands` and `allowedDomains` for the stack. Suggest, never configure: `/auto-mode-setup` and `/fewer-permission-prompts` (`autoMode` only counts in user settings, so setup writes none), the `security-guidance` plugin for web apps and repos with auth, and `/advisor opus` when the person works with Sonnet (builders inherit it). Entries use `Bash(...)` rule syntax, so add ` *` for arguments and keep them narrow (`docker compose *`, `latexmk *`); they run outside the sandbox, say so.
5. Cloud, only without other committers and with a GitHub remote: ask once whether runs may use the cloud. With yes: copy `${CLAUDE_PLUGIN_ROOT}` without `.claude-plugin/types` to `.slice/plugin`, copy `${CLAUDE_PLUGIN_ROOT}/templates/cloud-skill.md` to `.claude/skills/slice-cloud/SKILL.md`, set `"cloud": true` in the marker and commit the marker, `.slice/plugin` and the skill (cloud sessions see only what is committed). Say that the Claude GitHub App or `/web-setup` must give cloud sessions push access, and that cloud sessions count against the same usage limits.
6. Worktree root: supervised features and runs build their worktrees under `~/.cache/slice/`, which must be in `permissions.additionalDirectories` of the user settings. Check whether it is there; if not, confirm the root once with AskUserQuestion. Never edit the user settings yourself: print the exact line and let the person add it (or use the update-config skill on their request).
7. Last, write `.claude/slice.json` (at most 15 lines: `corePaths` as path prefixes of core logic such as `src/billing/`, `germanUiPaths`, `throwaway`, `excludedCommands`, `allowedDomains`, `cloud`) and add `.claude/slice.json` (unless the cloud step committed it), `.slice-env` and `CLAUDE.local.md` (if created) to `.git/info/exclude`. Create `.slice-env` with the repo's port, database and temp values so worktrees can differ. The file is the opt-in marker; restart the session so the mod loads it.

Finish with a list of the files written or changed. Never write plans, specs, progress files or a Markdown file per feature.
